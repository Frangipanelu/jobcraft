# 02 — 岗位分析模块产品设计

## 一句话定位

输入一段 JD，自动提取岗位画像，与用户的经历卡做匹配分析，输出差距分析与优化建议。

---

## 用户场景

用户在完成「经历梳理」后就进入了求职准备阶段。典型场景：

1. 用户看到心仪的岗位 JD（从招聘网站复制）
2. 粘贴 JD + 选择相关经历卡，发起分析
3. 系统返回：
   - 岗位画像（能力要求、硬技能、软技能、职责）
   - 每张卡的匹配分数
   - 覆盖项与缺失项
   - 具体的改写/补充建议
4. 用户根据建议优化经历卡内容
5. 系统生成针对性简历 Markdown

---

## 数据流（三段串联）

```
JD 文本
  │
  ▼
① ATS 解析（单次 LLM 调用）
  ├─ 岗位标题 / 部门 / 地点
  ├─ 硬技能列表 / 软技能列表 / 关键词
  ├─ 职责描述 / 量化指标
  ├─ D1-D8 维度要求（level 1-5 + 原文证据）
  │
  ▼
② 匹配计算
  ├─ 遍历用户选择的经历卡
  ├─ 优先用 ai_structured（成就文本）做匹配源
  │   └─ 无缓存时 fallback raw_text
  ├─ 本地关键词匹配（术语归一化 → 子串匹配 → tag 精确命中）
  ├─ LLM 语义评分（同一 prompt 内批量打分）
  └─ 融合：local × 0.4 + llm × 0.6 → 最终分数
  │
  ▼
③ 建议生成
  ├─ 规则层：低分卡 → 提示补充关键词
  ├─ 规则层：缺失项 → 建议补充对应经历
  └─ LLM 层：结合 JD + 卡片情况给出 3-5 条具体优化建议
```

---

## 匹配策略

### 匹配源优先级

| 优先级 | 源 | 说明 |
|--------|-----|------|
| 1 | `ai_structured.achievements[]` | 将 S/A/R 字段拼接为文本块进行匹配，结构清晰、噪声少 |
| 2 | `raw_text` | 无结构化缓存时退回到用户原始文本 |
| 3 | `tags` | 标签作为 hint，精确命中时权重更高（score=2 vs 文本命中 score=1） |

### 分数融合公式

```
本地匹配分 = Σ(每个术语命中得分) / 满分 × 100
最终分 = 本地分 × 0.4 + LLM 语义分 × 0.6
```

- 本地分看关键词是否在文本中出现（字面匹配）
- LLM 分看语义上是否覆盖了岗位要求（语义匹配）
- 两者互补：本地分防止 LLM 幻觉，LLM 分弥补同义词/近义表达

## 与经历卡架构的集成

经历卡重构（v0.2）后，岗位分析模块做了一处适配：

**`_card_text_blob()` 加入 `raw_text` 字段。**

这意味着无论新卡还是旧卡，都能被正确地匹配。当 ai_structured 缓存可用时，匹配函数优先拼接 achievements 的结构化文本（S/A/R），无缓存时回退到 raw_text。

### API 接口

| 方法 | 路径 | 请求体 | 返回 |
|------|------|--------|------|
| POST | `/api/jobcraft/job/analyze` | `{position, jd_text, card_ids}` | `{job_analysis_id, match_score, per_card_scores, gap_analysis, suggestions}` |

### 页面步骤（简化版）

之前的版本有 3 步（公司背调 → JD 分析 → 简历结果），**公司背调已裁剪**，改为：

```
┌─────────────────────────────────┐
│  ① 输入岗位名 + 粘贴 JD         │
│  ② 从经历列表勾选相关卡片       │
│  ③ 点击「分析」按钮              │
└─────────────────────────────────┘
              │
              ▼
┌─────────────────────────────────┐
│  结果面板（Tabs 分页）            │
│  ├─ 岗位画像（ATS 解析结果）      │
│  ├─ 匹配详情（每张卡分数 + 缺口） │
│  ├─ 优化建议（具体改写方案）      │
│  └─ 定制简历（预览 + 下载）      │
└─────────────────────────────────┘
```

## 设计决议摘要

| 决策 | 结论 | 理由 |
|------|------|------|
| 多 Agent vs 单 LLM | 三段串行单次 LLM 调用 | 每步有确定输入输出，不需要多智能体协作 |
| 公司背调 | 裁剪 | 搜索不准 + 缺免费 MCP + 偏离核心价值 |
| 匹配源 | 优先 ai_structured → fallback raw_text | 结构化文本匹配更准，无缓存时也不阻塞 |
| 评分算法 | local × 0.4 + llm × 0.6 | 字面匹配 + 语义匹配互补 |
| 建议生成 | 规则兜底 + LLM 增强 | 规则保证有输出，LLM 提高质量 |
