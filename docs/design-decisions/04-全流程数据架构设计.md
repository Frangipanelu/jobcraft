# 04 — 全流程数据架构设计

## 三流分离原则

经历卡片有「版本」，但版本不是卡片唯一的修改来源。全流程涉及三种内容，各自独立修改：

| 内容流 | 谁修改 | 存哪里 | 数据结构 |
|--------|--------|--------|----------|
| **经历文本** | 岗位分析（polish）、面试复盘（review_refined） | `card_versions` | 版本表，每版一条 |
| **面试答题稿** | 面试复盘后自省 | `prep_editions` | 每题/每段独立版本 |
| **Elevator pitch** | 面试复盘后自省 | `prep_editions` | 同上表，type 区分 |

三者为什么独立：
- 经历文本改的是**事实表述角度**，不改事实本身
- 答题稿改的是**回答策略**（same experience, different framing）
- Pitch 改的是**自我定位**（独立于任何单段经历）

## 版本表（`card_versions`）

```sql
CREATE TABLE card_versions (
  id            INT AUTO_INCREMENT PRIMARY KEY,
  card_id       INT NOT NULL,              -- FK → experience_card.id
  version_type  VARCHAR(32) NOT NULL,      -- 'polished' | 'review_refined'
  source_type   VARCHAR(32) NOT NULL,      -- 'job_analysis' | 'interview_review'
  source_id     INT NOT NULL,              -- job_analysis.id / interview_review.id
  title         VARCHAR(300),              -- 版本标题（可沿用原卡）
  raw_text      LONGTEXT NOT NULL,         -- 这个版本的文本
  ai_structured JSON,                      -- 这个版本的结构化缓存（可选）
  tags          JSON,                      -- 这个版本的标签（可选）
  note          TEXT,                      -- 用户备注（例如："这家公司看重技术深度，重点突出算法细节"）
  created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  KEY idx_card (card_id),
  KEY idx_source (source_type, source_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 版本类型的含义

| version_type | 什么时候创建 | 例子 |
|-------------|-------------|------|
| `polished` | 岗位分析后，用户确认润色建议后保存 | `"通过A/B测试优化转化链路，DAU提升40%"` |
| `review_refined` | 面试复盘后，用户发现经历可以讲得更好 | `"加了一段关于失败经验的反思"` |

### 查询时的版本选择

```
查最近一条 version_type='polished' AND source_id=当前岗位分析
  → 有则用
  → 无则 fallback card.raw_text
```

## 面试稿版本表（`prep_editions`）

```sql
CREATE TABLE prep_editions (
  id            INT AUTO_INCREMENT PRIMARY KEY,
  prep_id       INT NOT NULL,              -- FK → interview_preps.id
  edition_type  VARCHAR(32) NOT NULL,      -- 'pitch' | 'answer'
  question_key  VARCHAR(64),               -- edition_type='answer' 时，标识是哪道题
  text          LONGTEXT NOT NULL,         -- 修改后的文本
  source_review_id INT,                    -- 来自哪次复盘（可选）
  created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  KEY idx_prep (prep_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 使用场景

| edition_type | question_key | text |
|-------------|-------------|------|
| `pitch` | — | 修改后的 elevator pitch |
| `answer` | `d3_用户分层` | "关于用户分层，我应该先说RFM模型的选择逻辑..." |

## 全流程 4 个模块的数据通量（迭代后的设计）

### 模块 1：经历梳理

```
用户输入 raw_text
  ↓
存 experience_card（原始版本，永久不变）
  ↓
AI 自动抽取 ai_structured（S/A/R 缓存）
  ↓
用户手动调整 tags
```

### 模块 2：岗位分析

```
粘贴 JD
  ↓
① ATS 解析（LLM）
  ↓
② AI 推荐相关卡 + 用户审批
  ↓
③ 缺口分析 + 润色建议（LLM，一次性）
  ↓
④ 用户查看建议，逐卡确认/修改
  ↓
⑤ 用户编辑完成后，保存到 card_versions (version_type='polished')
  ↓
⑥ 生成简历 → 读 card_versions 或 fallback card.raw_text
```

### 模块 3：面试准备

```
基于岗位分析的 JD + 用户选的卡
  ↓
① 生成答题稿（LLM）
  ↓
  包含：
  - Elevator pitch
  - 按维度分的预测题 + 答题要点
  - 经历卡片引用
  ↓
② 用户可手动编辑答题稿（存 prep_editions）
```

### 模块 4：面试复盘

```
上传面试录音转写文本
  ↓
① 解析对话（规则拆 speaker）
  ↓
② 配对 QA（规则） + 意图分析（LLM）
  ↓
③ 评分 + 标准答案 + 反馈（LLM，只分析选中问题）
  ↓
④ 用户自省，可以：
  - 修改答题稿（存 prep_editions）
  - 修改经历文本（存 card_versions, version_type='review_refined'）
```

## 总结

| 设计决策 | 结论 |
|---------|------|
| 原卡修改？ | 不改。原卡 raw_text 是权威版本 |
| 定制文本存哪里？ | `card_versions` 表，type='polished' / 'review_refined' |
| 面试稿修改存哪里？ | `prep_editions` 表，独立于版本表 |
| 生成简历用什么文本？ | 优先读 `card_versions` 的最新 polished 版本，无则用原卡 raw_text |
| 跨岗位复用？ | 卡片列表标注"已为 xx 岗位定制过"，用户自行决定是否复用旧版本 |
